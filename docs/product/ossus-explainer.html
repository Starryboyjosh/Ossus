La idea principal

El catálogo puede ser enorme. El contexto no.

La plataforma separa lo que está disponible de lo que un agente puede leer. Tener una skill instalada no significa que su contenido se inyectará en cada conversación.

“Instalada no significa activa.”

El usuario puede mantener cientos o miles de recursos en una instalación global, local o personalizada. Para cada tarea, el resolver entrega únicamente las capacidades necesarias, fija sus versiones y explica por qué fueron seleccionadas.

Arquitectura funcional

Tres servicios. Un mismo repositorio.

Comparten formatos, políticas e índices, pero no comparten el mismo nivel de confianza ni los mismos permisos.

Researcher

Busca proyectos en fuentes como GitHub, Reddit o directorios públicos. No instala ni ejecuta nada por defecto: recopila evidencia, detecta riesgos y prepara un candidato para revisión.

discover()

Encuentra candidatos

Búsqueda por categoría, host, CLI, runtime, popularidad y mantenimiento.

inspect()

Analiza sin confiar

Trata README, prompts, scripts y manifiestos de origen como datos hostiles.

evidence.json

Genera evidencia

Licencia, commit, hash, permisos observados, señales comunitarias y hallazgos.

candidate/

Propone, no aprueba

Deja el candidato listo para la revisión humana correspondiente a su riesgo.

Registry

Es la fuente de verdad del ecosistema. Conserva manifiestos canónicos aprobados, hashes, compatibilidad y procedencia. Por defecto funciona como índice; descarga el contenido fijado por commit al instalar.

canonical-manifest

Metadatos controlados

Capabilities, triggers y permisos son revisados; no se importan ciegamente del autor.

approved/

Catálogo confiable

Solo contiene recursos que completaron la ruta de admisión correspondiente.

commit + hash

Procedencia reproducible

Una instalación puede verificar exactamente qué contenido recibió.

search index

Búsqueda estructurada

Filtra por categoría, host, CLI, portabilidad, riesgo y tipo de recurso.

Resolver

Lee el proyecto, interpreta la tarea y selecciona el conjunto mínimo suficiente. Trabaja primero con metadatos y reglas locales; un modelo es opcional y se usa solo en casos ambiguos.

scan project

Detecta el stack

Frameworks, dependencias, archivos, CI, bases de datos y herramientas disponibles.

capability graph

Traduce necesidades

Convierte la tarea en capacidades gobernadas y versionadas.

minimum cover

Evita redundancia

Elige la menor combinación que cubra la tarea sin conflictos innecesarios.

activate()

Adapta al host

Genera la estructura necesaria para Claude Code, Codex u otro destino compatible.

Modelo de confianza

El contenido cambia de zona, no de naturaleza.

Una skill aprobada sigue siendo un canal de instrucciones hacia el agente del usuario. La aprobación reduce el riesgo; no convierte el contenido en algo intrínsecamente seguro.

QUARANTINE

Contenido externo sin confianza

Se descarga fuera del catálogo principal. No se ejecuta, no recibe secretos y no entra al contexto del agente.

Paths del sistema

Dos recorridos explican todo el producto.

El primero muestra cómo opera el repositorio. El segundo sigue una skill desde su descubrimiento hasta su uso real dentro de un proyecto.

01

El catálogo se sincroniza

El usuario mantiene una copia global, local o personalizada de los manifiestos aprobados.

02

El resolver inspecciona el proyecto

Lee señales como package.json, pyproject.toml, dependencias, carpetas y configuración.

03

La tarea se convierte en capacidades

“Mejorar la landing” puede convertirse en diseño frontend, responsive, accesibilidad y validación visual.

04

Se filtran candidatos compatibles

Host, runtime, CLI, riesgo, permisos, versión, categoría y disponibilidad local.

05

Se calcula el conjunto mínimo

Se penalizan conflictos, redundancia, costo de contexto y permisos innecesarios.

06

El adaptador activa las skills

Se generan enlaces o archivos para el host objetivo sin copiar todo el catálogo dentro del proyecto.

07

Se escribe skills.lock

Quedan registradas versiones, hashes, fuentes y razones de selección para reproducir el entorno.

01

Descubrimiento

El Researcher encuentra una skill por categoría, repositorio, Reddit, referencia comunitaria o aportación manual.

02

Cuarentena

Se fija el commit, se calcula el hash y el contenido queda fuera del repositorio confiable.

03

Inspección automática

Licencia, archivos, scripts, instrucciones, permisos reales, mantenimiento y señales de reputación.

04

Clasificación de riesgo

Una skill declarativa puede seguir una vía ligera; una con shell, red, binarios o dependencias exige revisión completa.

05

Manifiesto canónico

Las capacidades, triggers, permisos y compatibilidad son redactados y firmados por el catálogo, no copiados del autor.

06

Revisión humana

Un revisor acepta, corrige, limita o rechaza la entrada según la evidencia y el riesgo.

07

Ingreso al Registry

La entrada aprobada pasa al índice principal con su commit, hash, licencia, categoría y compatibilidad.

08

Instalación o sincronización

El usuario la obtiene desde el catálogo oficial, una ruta local o una fuente privada priorizada.

09

Resolución para un proyecto

El Resolver la selecciona únicamente cuando sus capacidades y restricciones encajan con la tarea.

10

Activación y seguimiento

El adaptador la expone al agente, el lockfile fija la versión y futuras evaluaciones miden si la selección fue correcta.

Control del catálogo

El origen describe. El catálogo decide.

El sistema conserva dos perspectivas: lo que el proyecto afirma sobre sí mismo y lo que el repositorio verificó.

Origin manifest

Contenido extraído del repositorio fuente. Es evidencia, no autoridad.

  • Descripción escrita por el autor.
  • Permisos declarados.
  • Triggers sugeridos.
  • Compatibilidad afirmada.
  • Instrucciones y archivos originales.
source: repository: author/tool commit: 91d2f7a trust: unverified claims: capabilities: [...] permissions: [...] compatibility: [...]

Canonical manifest

Metadatos usados realmente por el buscador y el resolver.

  • Capacidades del vocabulario gobernado.
  • Permisos observados y límites.
  • Hosts y runtimes comprobados.
  • Riesgo y vía de revisión.
  • Commit, hash y firma de aprobación.
id: verified.impeccable type: skill capabilities: - frontend.design-review - frontend.responsive-layout compatibility: hosts: [claude-code-cli] runtime: local-shell trust: risk: R1 approved: true
Resolución local

Primero reglas. IA solo cuando aporta.

El resolver evita enviar todo el catálogo a un modelo. Detecta el proyecto de forma determinista, consulta un índice local y usa el vocabulario de capacidades para encontrar cobertura mínima.

Distribución

Un repositorio clonable, no una caja negra.

La misma instalación puede actuar como catálogo oficial, biblioteca personal o base para una investigación privada.

Orden de precedencia

Proyecto → biblioteca del usuario → catálogo oficial remoto.

El valor no está en guardar skills.

Está en saber de dónde vienen, qué pueden hacer, para qué host funcionan, qué riesgo representan y cuándo realmente conviene permitir que entren al contexto de un agente.
